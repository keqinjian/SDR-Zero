# 信息波 ROS 话题详细说明

> 对应程序：`competition/info/info_decoder_f1.py`  
> 协议：通信协议 V2.0.0（命令 `0x0A01`～`0x0A05`）  
> 消息类型：全部为 `std_msgs/msg/String`，内容是 **JSON 文本**（`ensure_ascii=False`）  
> 更新频率：官方信息波约 **10 Hz** 一轮；CRC 通过一帧就发一次对应话题（不是固定定时器）

---

## 0. 总览：信息波在系统里干什么？

```text
对方基座广播源（己方阵营频点）
    ↓ GFSK
Pluto RX + GNU Radio（competition/info/tx_radio.py）
    ↓ UDP 0/1 比特流 :14346
info_decoder_f1.py
    ↓ 解空口包 → 拼裁判帧 → 按 cmd 解析
ROS2 话题 radio/info/*
    ↓
雷达站上层（决策 / UI / 记录）
```

信息波 **不携带干扰密钥**（密钥在干扰波 `0x0A06` → `radar/jamming_key`）。  
这里发布的是：**对方机器人状态的「侦察情报」**——坐标、血量、弹药、场地占领、增益与姿态等。

语义要点：

| 概念 | 含义 |
|------|------|
| 数据内容 | 协议写的是「**对方**」各机器人 / 对方金币与占领等 |
| 射频听谁 | 听 **己方基座** 上的广播源（红 433.2 / 蓝 433.92 MHz） |
| 为何听己方 | 规则：广播源在己方基座，内容描述对方态势（与干扰源「己方发、带对方密钥」同理） |

另有一个 **订阅** 话题：`/team`，用来切己方阵营并改 GRC 频点。

## 1. 话题一览

| 话题名 | 协议命令 | data 长度 | 上层用途（典型） |
|--------|----------|-----------|------------------|
| `radio/info/position` | `0x0A01` | 24 B | 对方各车坐标 → 导航 / 预测 / 标定 |
| `radio/info/hp` | `0x0A02` | 12 B | 对方血量 → 威胁评估 / 优先打击 |
| `radio/info/ammo` | `0x0A03` | 10 B | 对方剩余可发弹量 → 交战节奏 |
| `radio/info/macro` | `0x0A04` | 8 B | 金币 + 场地占领/交互位图 → 宏观决策 |
| `radio/info/buff` | `0x0A05` | **41 B** | 增益、哨兵姿态、主要状态 → 状态机 / UI |
| `/team`（订阅） | — | Int8 | `0`=红方，`1`=蓝方 → 切听频点 |

键名约定（与旧 auto3 对齐，方便上层替换）：

| JSON 键 | 兵种 |
|---------|------|
| `hero` | 英雄 |
| `eng` | 工程 |
| `inf3` | 3 号步兵 |
| `inf4` | 4 号步兵 |
| `aerial` | 空中（仅部分话题有） |
| `sentry` | 哨兵 |

## 2. `radio/info/position`（0x0A01 坐标）

### 2.1 协议原始

- 12 个 `uint16` 小端，单位 **厘米（cm）**
- 顺序：英雄 xy、工程 xy、步兵3 xy、步兵4 xy、空中 xy、哨兵 xy

### 2.2 发布 JSON 示例

```json
{
  "hero": {"x": 2.5, "y": 3.1},
  "eng": {"x": 1.2, "y": 0.5},
  "inf3": {"x": 0.5, "y": 1.0},
  "inf4": {"x": 1.2, "y": 0.0},
  "aerial": {"x": 10.0, "y": 5.0},
  "sentry": {"x": 0.0, "y": 4.0},
  "unit": "m"
}
```

### 2.3 字段意义

| 字段 | 类型 | 意义 |
|------|------|------|
| `*.x` / `*.y` | float | 对方该兵种在场地坐标系下的位置 |
| `unit` | `"m"` | **已从 cm 除以 100**，上层按米用，勿再 ÷100 |

### 2.4 上层怎么用

- 雷达视觉跟踪的初值 / 校验、弹道或路径预测  
- 注意：无线电坐标是裁判侧给出的对方位置，**不是**本雷达视觉直接测距；可能有延迟与量化（cm 级）

---

## 3. `radio/info/hp`（0x0A02 血量）

### 3.1 协议原始

- 6 个 `uint16`：英雄、工程、步兵3、步兵4、**保留**、哨兵  
- 发布时 **丢掉保留位**，只出 5 个兵种

### 3.2 发布 JSON 示例

```json
{
  "hero": 2000,
  "eng": 500,
  "inf3": 800,
  "inf4": 800,
  "sentry": 600
}
```

### 3.3 字段意义

| 字段 | 意义 |
|------|------|
| 各键数值 | 对方该兵种当前血量（与裁判系统一致的整型血量） |

### 3.4 上层怎么用

- 判断对方是否残血、是否已倒（配合 `buff.main_status` 更稳）  
- 优先级：例如残血英雄优先标记

---

## 4. `radio/info/ammo`（0x0A03 允许发弹量）

### 4.1 协议原始

- 5 个 `uint16`：英雄、步兵3、步兵4、空中、哨兵  
- **无工程**（工程通常不依赖此弹种计数）

### 4.2 发布 JSON 示例

```json
{
  "hero": 150,
  "inf3": 450,
  "inf4": 400,
  "aerial": 500,
  "sentry": 800
}
```

### 4.3 字段意义

| 字段 | 意义 |
|------|------|
| 各键数值 | 对方该兵种当前 **允许发射的弹药量**（裁判侧计数） |

### 4.4 上层怎么用

- 估计对方压制能力、是否可能突然「空仓」  
- 与视觉「是否在射击」结合做威胁模型

---

## 5. `radio/info/macro`（0x0A04 金币与占领）

### 5.1 协议原始

- `uint16 coin`：当前金币  
- `uint16 total_coin`：累计金币  
- `uint32 status`：占领 / 交互状态位图（小端，协议表约 1-47）

### 5.2 发布 JSON 示例

```json
{
  "coin": 350,
  "total_coin": 1200,
  "occupation": {
    "supply": 0,
    "center_highland": 0,
    "trapezoid_highland": 0,
    "fortress": 0,
    "outpost_buff": 0,
    "base_buff": 1,
    "enemy_tunnel_pre": 0,
    "enemy_tunnel_post": 0,
    "ally_tunnel_pre": 0,
    "ally_tunnel_post": 0,
    "enemy_highland_top": 0,
    "enemy_fly_ramp_rear": 0,
    "enemy_highway_top": 0,
    "raw_bits": 256
  }
}
```

### 5.3 字段意义

| 字段 | 位来源 | 意义（概要） |
|------|--------|--------------|
| `coin` | — | 对方当前可用金币 |
| `total_coin` | — | 对方本局累计获得金币 |
| `occupation.supply` | bit0 | 补给区相关占领/状态（0/1） |
| `occupation.center_highland` | bit1–2 | 中央高地（2 bit，取值 0～3） |
| `occupation.trapezoid_highland` | bit3 | 梯形高地 |
| `occupation.fortress` | bit4–5 | 堡垒（2 bit） |
| `occupation.outpost_buff` | bit6–7 | 前哨站增益相关（2 bit） |
| `occupation.base_buff` | bit8 | 基地增益点是否占领等（0/1） |
| `occupation.enemy_tunnel_pre` | bit9 | 检测到对方：飞坡隧道前 |
| `occupation.enemy_tunnel_post` | bit10 | 检测到对方：飞坡隧道后 |
| `occupation.ally_tunnel_pre` | bit11 | 己方侧隧道前交互检测 |
| `occupation.ally_tunnel_post` | bit12 | 己方侧隧道后 |
| `occupation.enemy_highland_top` | bit13 | 对方高地顶部 |
| `occupation.enemy_fly_ramp_rear` | bit14 | 对方飞坡后侧 |
| `occupation.enemy_highway_top` | bit15 | 对方公路顶部 |
| `occupation.raw_bits` | 全 32 位 | 原始位图，便于调试 / 协议升级时自解 |

> 多 bit 字段（如中央高地）的 **枚举含义以当年通信协议表为准**；decoder 只做位移拆出，不做赛季特判文案。

### 5.4 上层怎么用

- 宏观策略：是否抢增益点、是否防飞坡、经济差  
- UI 显示「对方已占基地增益」等  
- 新规则场地交互 bit9～15：用于「对方是否触发某模块」类逻辑

## 6. `radio/info/buff`（0x0A05 增益 / 姿态 / 主要状态）

### 6.1 为何最重要（V2）

旧版 data **36** 字节；V2 改为 **41** 字节：

| 偏移 | 长度 | 内容 |
|------|------|------|
| 0～34 | 35 | 5 兵种 × 7 字节增益 |
| 35 | 1 | 哨兵姿态（枚举扩展到 1～6） |
| 36～40 | 5 | 英雄/工程/步兵3/步兵4/哨兵 **主要状态**（新增） |

仍按 36 解析会导致帧边界错乱，后面所有话题都会废。

### 6.2 单兵种 7 字节增益布局

每个单位（hero / eng / inf3 / inf4 / sentry）：

| 字段 | 类型 | JSON 键 | 意义 |
|------|------|---------|------|
| 回血 | uint8 | `heal_pct` | 回血相关百分比 |
| 冷却 | uint16 | `cooling` | 冷却数值 |
| 防御 | uint8 | `defense_pct` | 防御百分比 |
| 负防御 | uint8 | `negative_defense_pct` | 负防御 / 易伤侧（协议名） |
| 攻击 | uint16 | `attack_pct` | 攻击百分比 |

兼容旧上层字段名（同值）：

- `vulnerability` ≡ `negative_defense_pct`  
- `attack` ≡ `attack_pct`

### 6.3 哨兵姿态（offset 35）

| code | `sentry_posture_name` | 含义（V2） |
|------|----------------------|------------|
| 1 | `attack` | 进攻 |
| 2 | `defense` | 防御 |
| 3 | `move` | 移动 |
| 4 | `attack_enhanced` | 强化进攻（新规则） |
| 5 | `defense_enhanced` | 强化防御（新规则） |
| 6 | `move_enhanced` | 强化移动（新规则） |

### 6.4 主要状态（offset 36～40）

每个兵种一个 `uint8`：

| code | `name` | 含义 |
|------|--------|------|
| 0 | `alive` | 存活 |
| 1 | `dead` | 战亡 |
| 2 | `invincible` | 无敌但不虚弱 |
| 3 | `invincible_weak` | 无敌且虚弱 |

说明：异常离线不改变此处判断（以协议为准）。

### 6.5 发布 JSON 示例

```json
{
  "units": {
    "hero": {
      "heal_pct": 10,
      "cooling": 100,
      "defense_pct": 20,
      "negative_defense_pct": 0,
      "attack_pct": 150,
      "vulnerability": 0,
      "attack": 150
    },
    "eng": { "...": "..." },
    "inf3": { "...": "..." },
    "inf4": { "...": "..." },
    "sentry": { "...": "..." }
  },
  "sentry_posture": 2,
  "sentry_posture_name": "defense",
  "main_status": {
    "hero": {"code": 0, "name": "alive"},
    "eng": {"code": 0, "name": "alive"},
    "inf3": {"code": 0, "name": "alive"},
    "inf4": {"code": 0, "name": "alive"},
    "sentry": {"code": 0, "name": "alive"}
  }
}
```

### 6.6 上层怎么用

- **增益**：判断对方是否开大防御/攻击，调整自己交战窗口  
- **哨兵姿态**：哨兵策略、是否可打、是否在机动  
- **主要状态**：比单纯血量=0 更干净的「死/无敌」标志，避免误判

## 7. 订阅 `/team`（阵营，不是情报）

| 类型 | 值 | 效果 |
|------|-----|------|
| `std_msgs/Int8` | `0` | 己方=红 → 听 433.2 MHz |
| | `1` | 己方=蓝 → 听 433.92 MHz |

切阵营时 decoder 会：

1. XMLRPC 改 GRC `target_freq`  
2. 清空接收缓冲（避免把另一路信号拼进本轮帧）

未收到 `/team` 时，使用代码里 `MY_CAMP` 默认值（通常 `"RED"`）。**上场务必由裁判/车队发对 `/team`。**

## 8. 发布时机与可靠性

| 点 | 说明 |
|----|------|
| 何时发 | 对应 `0x0A0x` **CRC 通过且长度符合** 后立即 `publish` |
| 是否整轮五条齐发 | 不一定；某一帧先解出就先发该话题 |
| 丢包表现 | 某一话题短时间不更新；上层应用时间戳或「超时变旧」逻辑 |
| 假数据 | Header/CRC 门闩后才解析；勿把未校验的 UDP 当情报 |

建议上层：

```text
订阅五条 radio/info/* 
  → JSON 反序列化
  → 带 receive_time
  → 超过 N 秒未更新则标记 stale
```

## 9. 与干扰波话题的边界

| | 信息波 | 干扰波 |
|--|--------|--------|
| Decoder | `info_decoder_f1` | `jamming_decoder_f2` |
| 话题 | `radio/info/*` | `radar/jamming_key`（+ meta） |
| 内容 | 对方态势情报 | 6 位 ASCII 密钥 |
| 上报裁判 | 一般不上 `0x0121` | 密钥走 `0x0121` 验证 |

不要把信息波 JSON 里的字段当成密钥；也不要在信息波里等 `0x0A06`。

## 10. 快速自检

```bash
# 终端看原始 JSON
ros2 topic echo /radio/info/position
ros2 topic echo /radio/info/hp
ros2 topic echo /radio/info/ammo
ros2 topic echo /radio/info/macro
ros2 topic echo /radio/info/buff

# 切阵营
ros2 topic pub --once /team std_msgs/msg/Int8 "{data: 1}"
```

日志侧：`info_decoder_f1` 每 5s 统计里 `0x0A01`～`0x0A05` 计数应随空口上涨；若只有 UDP 字节、业务帧为 0，先查物理层而非上层话题语义。
