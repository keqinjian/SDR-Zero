# 投票机制说明 & 完成版相对初版的改进总结

> 适用代码：`competition/jamming/jamming_decoder_f2.py`、`competition/info/info_decoder_f1.py`  
> 规则基准：通信协议 V2.0.0 + 规则手册 V2.1.0  
> 对照起点：仓库最初版（`jamming_decoder_f1` / `info_decoder_auto*`、旧 SPS=52、听敌方频点、`0x0A05`=36 等）

---

## 一、投票机制是什么？（干扰波密钥恢复）

### 1.1 一句话

**在 CRC 暂时过不了时，把多份「看起来像密钥」的 6 字节凑在一起，按位选出现次数最多的字符，拼出一把候选密钥。**

它是 **CRC 严格路径的备份**，不是主路径。默认只发到 `radar/jamming_key_meta`，**不进**正式话题 `radar/jamming_key`（避免误报去打 `0x0121`）。

### 1.2 为什么需要它？

干扰波 `0x0A06` 整帧恰好 **15 字节 = 1 个空口 Payload**，结构简单，但空口仍会有偶发误码：

| 路径 | 条件 | 结果 |
|------|------|------|
| **严格路径** | CRC8 + CRC16 全过，且 6 位全是字母数字 | 认定真密钥 → 发 `radar/jamming_key` |
| **投票路径** | 多份候选里「多数票」拼出合法密钥 | 可能对、也可能错 → 默认只发 meta |

弱信号/切频瞬间，常出现：**Access/Header 已经对上了，但 CRC 偶发失败**。  
此时整帧作废很可惜——密钥那 6 个字节里，往往只有 1～2 个被打花。多收几份再投票，有机会还原。

### 1.3 流水线（对照代码）

```text
GFSK 解调比特流
    ↓
找 Access（正/反相模糊 48 bit）+ Header 门闩 → 抽出 15B Payload
    ↓
┌──────────────────────────────────────────┐
│ ① 收集投票候选（不要求 CRC 通过）          │
│    looks_like_jam_payload()：              │
│      · 以 A5 开头                          │
│      · data_len 像 6                       │
│      · cmd 像 0x0A06（允许少量 bit 错）    │
│      · key 区至少 4 个可打印字母数字       │
│    → 把 payload[7:13] 丢进 vote_pool       │
└──────────────────────────────────────────┘
    ↓
┌──────────────────────────────────────────┐
│ ② 严格解析（要求 CRC 全过）                │
│    → 每次成功都 publish radar/jamming_key  │
└──────────────────────────────────────────┘
    ↓
┌──────────────────────────────────────────┐
│ ③ 若尚未锁定，且候选 ≥ 3 份：              │
│    vote_key_from_candidates()              │
│      对第 0～5 字节分别统计出现次数        │
│      只统计字母/数字；该字节票数 ≥ 2 才采纳│
│      6 字节都成功 → 合法密钥               │
│    → publish meta（source=recovered）      │
└──────────────────────────────────────────┘
```

相关常量（`jamming_decoder_f2.py`）：

| 常量 | 默认 | 含义 |
|------|------|------|
| `KEY_VOTE_MIN_CANDIDATES` | 3 | 至少 3 份候选才投票 |
| `KEY_VOTE_MIN_PER_BYTE` | 2 | 每个位置至少 2 票才信 |
| `PUBLISH_RECOVERED_KEY` | `False` | 投票结果是否进主话题 |

### 1.4 小例子

假设真实密钥是 `Taurus`，三次「像密钥帧」的 6 字节分别是：

```text
候选1: T a u r u s
候选2: T a u r u X   ← 末字节花了
候选3: T a X r u s   ← 第 3 字节花了
```

逐字节多数票：

| 位置 | 票数最高 | 结果 |
|------|----------|------|
| 0 | T×3 | T |
| 1 | a×3 | a |
| 2 | u×2（对 X×1） | u |
| 3 | r×3 | r |
| 4 | u×3 | u |
| 5 | s×2（对 X×1） | s |

→ 恢复出 `Taurus`。单看候选 2 或 3，CRC 都会失败。

### 1.5 使用注意（赛场）

1. **上报裁判请只用严格 CRC 密钥**（`source=strict` / 主话题）。  
2. 投票有假阳性可能（噪声凑出「像」密钥的字节），故默认 `PUBLISH_RECOVERED_KEY=False`。  
3. 仅在「长时间 CRC 过不了、但 meta 里 recovered 很稳」时，才考虑人工打开投票主话题做调试。  
4. 信息波 **没有** 这套投票：信息波跨多包拼接，错 1 片整轮就错，投票帮不上忙；靠的是同步门闩 + 增益 + SPS/Sens 对齐。

## 二、完成版相对最初版改进了什么？

「最初版」指你最初交付/仓库里的旧实现：双 Pluto 架构已有，但物理参数、阵营语义、信息波同步、协议长度等仍按旧规则或存在已知缺陷。

### 2.1 总览对比

| 维度 | 最初版（典型） | 完成版（当前主路径） |
|------|----------------|----------------------|
| 规则口径 | 旧 SPS=52、旧 Sens、`0x0A05`=36 | **V2：SPS=47、新 Sens 表、`0x0A05`=41** |
| 信息波 decoder | auto 系列 / 弱同步 | **`info_decoder_f1`** |
| 干扰波 decoder | `jamming_decoder_f1` | **`jamming_decoder_f2`** |
| 听谁的频点 | 干扰侧常按 **敌方** 扫 | **己方基座（ally_camp）** |
| GRC | 常混 TX+RX、旧参数 | **纯 RX**；Sens RPC 真正生效 |
| 测试手段 | 缺完整 RF 环回 | **基带 mock + 交叉 RF mock** |
| 文档 | 少 / 与代码脱节 | V2 变更说明 + 缺陷对照 + 本总结 |

主路径文件：

```text
competition/info/tx_radio.py          + info_decoder_f1.py
competition/jamming/tx_radio.py       + jamming_decoder_f2.py
```

### 2.2 物理层（对齐规则 V2）

| 改进 | 说明 |
|------|------|
| SPS 52→**47** | 符号变密；不改则定时整体错位，「收得到解不出」 |
| 信息 Sens → **1.5628** | 旧 1.5756 |
| 干扰 Sens → **2.8194 / 2.5681 / 0.6517** | 旧 2.8323 / 2.5809 / 0.6646 |
| `gain_mu=0.175`、`freq_error=0.0048` | 弱信号符号时钟更稳（信息波尤其重要） |
| 信息波 RX gain 提到约 **45** | 官方约 -60 dBm，增益不够会直接解不出 |
| 信息波保留约 300 kHz LPF | 抑制邻道，保护解调 |

### 2.3 协议层

| 改进 | 说明 |
|------|------|
| **`0x0A05` 36→41** | 增益 35B + 哨兵姿态 1B + 主要状态 5B；仍按 36 切会全链路错位 |
| `CMD_DATA_LEN` 门闩 | CRC 后再核长度，防脏帧 |
| `0x0A04` 状态位解析补全 | bit0～15（含场地交互等）按协议展开 |
| 不再兼容旧 36B | 避免赛场混用假通过 |

### 2.4 阵营语义（修旧 bug）

| 最初版 | 完成版 |
|--------|--------|
| 干扰 `enemy_camp`：红方去听蓝方干扰频 | **`ally_camp`**：红听红基座三级频点 |
| 几何上与「干扰源在己方基座、带对方密钥」矛盾 | 与规则一致；`/team` 切换后立即切频并清缓冲 |

信息波同样：听 **己方广播源**（红 433.2 / 蓝 433.92），不是听对方。

### 2.5 空口同步与容错（信息波能解的关键）

最初版常见问题：假同步后跳过整包、Header 不严、极性处理弱 → 信息波连续包被「连坐」丢掉。

完成版 `info_decoder_f1` / `jamming_decoder_f2`：

| 机制 | 作用 |
|------|------|
| 正/反相双搜 Access（后 48 bit 模糊） | 解调极性反了也能挂上 |
| **Header 必须 `00 0F 00 0F`** | 降低假阳性 |
| Access 前缀汉明距离复核 | 模糊命中后再精修 |
| **失败只前进 1 bit** | 不再跳过 216 bit，避免漏真包 |
| 干扰侧密钥投票 | CRC 偶发失败时的备份（见第一节） |
| 干扰密钥 **每次 CRC 通过都发话题** | 不只在密钥变化时发 |

### 2.6 GNU Radio / 工程化

| 改进 | 说明 |
|------|------|
| RX 去掉 Pluto Sink / GFSK Mod | 纯收，避免误发射、抢资源 |
| `set_target_sens` → **`fmdemod.set_gain(1/sens)`** | GR 3.8.5 正确写法；旧 GRC 只改变量等于空操作 |
| GRC 路径相对 `__file__` / 环境变量 | 换机不必改死路径 |
| UDP 看门狗重启 GRC | 解调卡死可自愈（可用环境变量关掉） |
| 进程组杀掉旧 GRC | 减少僵尸进程占端口 |
| 双板 URI/端口写死约定 | A=jam `2.1:8080/14348`；B=info `3.1:8081/14346` |

### 2.7 测试与 Mock（最初版几乎没有）

| 工具 | 用途 |
|------|------|
| `rm_info_mock_v2.py` / `rm_jamming_mock_v2.py` | 基带直接喂 0/1 → 专测 decoder（跳过射频） |
| `competition/info_mock/` | 借 SDR-A 发信息波，SDR-B 收 |
| `competition/jamming_mock/` | 借 SDR-B 发干扰波，SDR-A 收 |
| decoder 启动自检 | 正相/反相/组帧/CRC 离线冒烟 |

交叉测已验证 info / jamming 一发一收均可通。

### 2.8 相对最初版：刻意没改 / 仍依赖上层的部分

| 项 | 说明 |
|----|------|
| 双 Pluto 并行架构 | 保留（开源是单 SDR 时分；你们赛场方案合理） |
| `0x0121` 密钥上报 | 仍在上层裁判链路；本仓只发 ROS 话题 |
| 投票默认不上主话题 | 保守策略，减少误报 |
| 旧文件仍留在仓库 | `jamming_decoder_f1`、`info_decoder_auto3`、根目录旧 `tx_radio.py`、`rm_referee_mock`（0x0A05=36）→ **上场禁止启动** |

## 三、赛场一句话备忘

- **主路径**：`info_decoder_f1` + `jamming_decoder_f2` + 两边纯 RX `tx_radio.py`。  
- **投票**：干扰波 CRC 失败时的多数票备份；正式破译请信严格 CRC。  
- **最大风险**：误跑旧 decoder / 旧 mock，而不是再漏改某个 Sens 小数。
